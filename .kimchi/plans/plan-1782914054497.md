## Goal
Implement an end-to-end signup flow that mirrors the existing login flow: the JavaFX client calls the Local Server, the Local Server persists the new user locally and emits a `USER_REGISTERED` outbox event, and the Central System creates the corresponding global user when it receives the sync event.

## Constraints
- No new external dependencies; use Spring Boot, JPA, BCrypt, Jackson and JavaFX already present.
- Preserve the existing `/api/users` public registration endpoint in the Central System.
- Keep the Clean Architecture / Hexagonal layering: domain ports & models → application services → infrastructure adapters.
- Follow the existing outbox + scheduler resilience pattern already used for sessions/reservations.
- Do not modify `UserSyncDto` (central→local replication contract).
- Update `infrastructure/mysql-local/init.sql` so a fresh Docker environment gets the needed schema.

## Decision Log
| Decision | Rationale | Rejected alternative |
|---|---|---|
| Local server persists signups in the existing `users` table, not `replicated_users`. | Matches the user’s explicit choice and keeps the two user sources separated. | Extending `replicated_users` with email. |
| Login lookup checks `replicated_users` first, then `users`. | Central-replicated data is the global source of truth; local signups are authoritative only until replication occurs. | Querying local users first or merging rows. |
| Signup is propagated via the outbox/scheduler, not a synchronous REST call. | Matches the user’s explicit choice and preserves offline-first resilience. | Direct `RestTemplate` call to `/api/users`. |
| The local server generates the UUID; central creates the user with that same UUID. | Needed for the offline-first outbox model so the local DB already has a stable id. | Central generating the UUID and returning it. |
| Sync-origin registrations in central do **not** create a central outbox event. | Prevents the central replication scheduler from pushing the same user back into `replicated_users` and creating redundant rows. | Reusing `UserService.saveUserOnDB`, which always publishes a replication event. |
| `UserRegisteredEventDto` is a new shared DTO rather than reusing `UserSyncDto`. | `UserSyncDto` intentionally omits email; the sync event needs email for central storage. | Adding email to `UserSyncDto` and changing the replication contract. |

## Risks
| Risk | Likelihood | Mitigation |
|---|---|---|
| Local `users` table schema change (unique constraints) conflicts with `ddl-auto: validate` and existing volumes. | Medium | Update `infrastructure/mysql-local/init.sql`; instruct team to recreate volumes with `docker-compose down -v` or run a manual `ALTER TABLE` on existing DBs. |
| Two user tables may confuse future maintainers or cause duplicate rows. | Medium | Document precedence (`replicated_users` first) and the reason for the split in README/code comments. |
| Updating the local exception handler changes the existing `AuthControllerTest` expectation for unknown users (500 → 404). | Low | Update the test in the same change set; behavior is more correct. |
| Central receives a `USER_REGISTERED` event for a username/email that already exists under a different id. | Low | `UserService.registerFromSync` detects the conflict, logs it, and treats the event as processed to avoid retry loops. |
| Client-side SSL trust store may reject the local server HTTPS certificate during signup. | Low | Client already uses the same `HttpClientHelper` as login; if login works, signup will work. |
